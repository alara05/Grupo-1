00 — Fundamentos DDL

CREATE · ALTER · DROP

⚠️

Regla crítica del DDL: todo comando DDL ejecuta un COMMIT automático. Una vez ejecutado, no existe ROLLBACK posible para deshacer el cambio de estructura.

🏗️

CREATE TABLE

Crea una estructura vacía con columnas, tipos de dato y restricciones definidas desde el inicio.

CREATE TABLE PRODUCTO ( ID NUMBER PRIMARY KEY, NOMBRE VARCHAR2(100), PRECIO NUMBER(10,2) );
✏️

ALTER TABLE

Modifica una tabla existente: añade columnas, cambia tipos o agrega/elimina restricciones.

ALTER TABLE PRODUCTO ADD STOCK NUMBER DEFAULT 0; -- Añadir un constraint: ALTER TABLE PRODUCTO ADD CONSTRAINT CK_PRECIO CHECK (PRECIO > 0);
🗑️

DROP TABLE

Destruye la tabla y todos sus registros permanentemente. En Oracle 10g+ va a la papelera de reciclaje.

DROP TABLE PRODUCTO; -- Recuperar con FLASHBACK: FLASHBACK TABLE PRODUCTO TO BEFORE DROP;
🔧

Truco profesional con ALTER: Si añades una columna NOT NULL a una tabla con datos existentes, Oracle fallará. La solución: (1) agrega la columna permitiendo NULL → (2) UPDATE con valor genérico → (3) modifica la columna a NOT NULL.

00b — Restricciones

Los 5 Constraints Fundamentales

PK

PRIMARY KEY

Identificador único e irrepetible. No permite valores nulos. Solo puede haber una por tabla. Crea índice automático.

FK

FOREIGN KEY

Integridad referencial. El valor debe existir previamente en la tabla padre. Base de las relaciones entre tablas.

UQ

UNIQUE

Asegura que los valores no se repitan en la columna. Permite NULL (varios registros pueden ser NULL). Pueden existir múltiples por tabla.

CK

CHECK

Valida condiciones de negocio específicas. Ejemplo: ESTADO IN ('A','I') o PRECIO > 0.

NN

NOT NULL

Obliga a que la columna siempre contenga un dato. Es el constraint más simple y uno de los más importantes para garantizar la calidad de los datos.

01 — Concepto

¿Qué es ON DELETE CASCADE?

Es una restricción de clave foránea que indica que al eliminar un registro padre, todos los registros hijos relacionados serán eliminados automáticamente por el motor de base de datos, manteniendo la integridad referencial sin errores.

🔗

Sin ON DELETE CASCADE, intentar borrar un padre que tiene hijos activos lanza un error de violación de integridad: integrity constraint violated – child record found. Con CASCADE, ese proceso se hace de forma encadenada y automática.

cliente_pedido.sql 
-- ① TABLA PADRE
CREATE TABLE CLIENTE (
    ID_CLIENTE  NUMBER        PRIMARY KEY,
    NOMBRE      VARCHAR2(50)
);

-- ② TABLA HIJA  →  ON DELETE CASCADE
CREATE TABLE PEDIDO (
    ID_PEDIDO    NUMBER  PRIMARY KEY,
    FECHA_PEDIDO DATE,
    ID_CLIENTE   NUMBER,
    FOREIGN KEY (ID_CLIENTE)
        REFERENCES CLIENTE(ID_CLIENTE)
        ON DELETE CASCADE          -- ← clave
);

-- ③ Al borrar el cliente, sus pedidos se borran solos
DELETE FROM CLIENTE
WHERE ID_CLIENTE = 1;
✓   1 fila eliminada en CLIENTE  |  3 filas eliminadas en PEDIDO (automático)
02 — Criterio de uso

¿Cuándo usarlo y cuándo no?

✅ SÍ usar CASCADE

  • Los hijos no tienen sentido sin el padre
  • Cliente → Pedidos
  • Carrito → Ítems del carrito
  • Factura → Líneas de factura
  • Publicación → Comentarios

🚫 NO usar CASCADE

  • Los hijos son valiosos por sí solos
  • Empleado → Historial de pagos
  • Usuario → Registros de auditoría
  • Paciente → Historial médico
  • Cualquier dato legal o regulatorio
empleado_historial.sql 
-- TABLA PADRE
CREATE TABLE EMPLEADO (
    ID_EMPLEADO NUMBER       PRIMARY KEY,
    NOMBRE      VARCHAR2(50)
);

-- TABLA HIJA SIN CASCADE  →  los registros sobreviven al padre
CREATE TABLE HISTORIAL_PAGOS (
    ID_PAGO     NUMBER         PRIMARY KEY,
    FECHA_PAGO  DATE,
    MONTO       NUMBER(10,2),
    ID_EMPLEADO NUMBER,
    CONSTRAINT FK_PAGO_EMPLEADO
        FOREIGN KEY (ID_EMPLEADO)
        REFERENCES EMPLEADO(ID_EMPLEADO)
        ON DELETE NO ACTION        -- ← protege los datos
);

-- Intento de borrar empleado con historial activo
DELETE FROM EMPLEADO
WHERE ID_EMPLEADO = 5;
✗   ERROR: integrity constraint violated – child record found  (comportamiento esperado y correcto)

04 — Resumen comparativo

CASCADE vs NO ACTION

✅ ON DELETE CASCADE

Elimina automáticamente todos los hijos cuando se borra el padre. Ideal para datos dependientes.

  • 🛒 Carrito → ítems del carrito
  • 🧾 Factura → líneas de factura
  • 💬 Post → comentarios
  • 📦 Cliente → pedidos
🚫 ON DELETE NO ACTION

Bloquea el borrado del padre si existen hijos. Protege datos históricos o de auditoría.

  • 💰 Empleado → historial de pagos
  • 🔍 Usuario → log de auditoría
  • 🏥 Paciente → historial médico
  • 📋 Cualquier dato regulatorio
⚡

Regla práctica: Pregúntate — "¿tiene sentido este registro hijo si el padre no existe?" Si la respuesta es NO → usa CASCADE. Si la respuesta es SÍ (el registro tiene valor propio) → usa NO ACTION o SET NULL.
